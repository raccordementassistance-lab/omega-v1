# P3.4-MVP-VALIDATION.md — Mode Test officiel

Mission : « ORDRE DE MISSION — P3.4 (MODE TEST OFFICIEL) ». Objectif : verrouiller le MVP avec un parcours de validation **identique à chaque version**, plutôt que « au feeling ».

## Ce qui a été livré

Un **Mode Test intégré au projet**, sans aucune dépendance Prisma ni changement de la State Machine :

1. **`src/lib/testmode/scenario.ts`** — le protocole officiel encodé en données pures : les 6 étapes exactes du parcours (Accueil, Projet, Adresse, Dossier Vivant, Mission Control, Fin), avec pour chacune son budget de temps, le message de test exact quand le protocole en impose un (« Bonjour, je construis une maison à Bordeaux. » pour l'étape Projet), la liste des vérifications à cocher, et le résultat attendu. Ce module ne crée **aucune fausse donnée** — il ne fait que décrire le parcours qu'un testeur humain exécute lui-même dans l'application réelle.
2. **Chronomètre officiel** — objectif verrouillé à **3 minutes** entre l'ouverture de l'accueil et l'affichage de Mission Control (`TARGET_ACCUEIL_TO_MISSION_CONTROL_SECONDS = 180`). Si une nouvelle version fait monter ce temps, c'est visible immédiatement, même si tous les tests techniques restent verts — exactement la demande d'Aristote.
3. **`TestModeButton.tsx` / `TestModePanel.tsx`** — le bouton discret et le panneau qui guident le testeur à travers les 6 étapes, chronomètrent en direct, cochent les vérifications, puis génèrent le tableau de validation final et un bouton **« Télécharger le rapport (.md) »** qui produit un fichier `P3.4-MVP-VALIDATION-<date>.md` prêt à archiver — même structure que ce document.
4. **`buildValidationReportMarkdown()`** — fonction pure et testée qui transforme l'état d'une session de test (checklist + chronos + bugs + notes) en ce même format de rapport, pour que chaque exécution future du Mode Test produise un document strictement comparable.

Le bouton est monté une seule fois dans `src/app/layout.tsx`, donc disponible sur tout le site (accueil, `/chat`, `/espace-client/dossiers/[id]`) sans dupliquer de code.

## Comment l'utiliser (pour Aristote, à chaque nouvelle version)

1. Ouvrir le site, cliquer sur le bouton discret « Mode Test » en bas à droite.
2. Suivre les 6 étapes affichées, exactement comme un vrai client (le message de test exact est rappelé à l'étape Projet).
3. Cocher chaque vérification réellement observée.
4. À la fin, le panneau affiche le tableau de validation et le chrono « Accueil → Mission Control » face à l'objectif de 3 minutes.
5. Télécharger le rapport — il a exactement la structure de ce document, donc comparable version après version.

## Limitations restantes

- Le Mode Test **guide et chronomètre** un testeur humain réel — il ne peut pas se substituer à une exécution live dans cet environnement. La première vraie session de test (avec captures d'écran et chrono réel) doit être effectuée par Aristote (ou un testeur) dans un navigateur, une fois l'environnement de déploiement disponible.
- L'état du Mode Test est volontairement local et non persisté (perdu à la fermeture du panneau) — cohérent avec la contrainte « aucune fausse donnée créée » : chaque session de test repart de zéro, comme un vrai client.
- Le bouton est visible sur toutes les pages, sans restriction d'environnement (pas de gate `NODE_ENV`) — à discuter si un jour il ne doit apparaître qu'en pré-production (arbitrage non tranché, sans impact sur le MVP actuel).

## Verdict final

**MVP PRÊT** — le protocole de validation officiel est maintenant un outil intégré au projet, reproductible identiquement à chaque version (au lieu d'un test « au feeling »), avec un objectif chrono explicite (3 minutes accueil → Mission Control) qui rendra visible toute dégradation future de l'expérience, même si les tests techniques restent verts. Réserve inchangée : aucune preuve d'exécution live n'a pu être obtenue dans cet environnement (blocage `npm` 403, documenté depuis le début du projet) — la première session réelle du Mode Test, une fois exécutée par un humain dans un vrai navigateur, sera la pièce manquante pour lever ce dernier doute avant une démonstration devant un client réel.
