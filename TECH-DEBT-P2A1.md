## 2. Risques

- **Risque de régression silencieuse sur `route.ts`** : c'est le seul fichier de toute la chaîne qui n'a jamais pu être réellement compilé ni exécuté dans cet environnement (uniquement relu). Le champ Zod ajouté (`addressDraft`) a été vérifié par lecture attentive (rétrocompatibilité `.optional().transform()`), mais une erreur de syntaxe ou de typage resterait invisible jusqu'à la première compilation réelle. **Atténuation recommandée** : faire de la tâche P2B.5 (`npm install` + build réel) une priorité avant tout ajout supplémentaire à ce fichier, pour ne pas accumuler plusieurs changements jamais compilés.
- **Risque d'expérience utilisateur dégradée sans signal clair** : quand la BAN est indisponible (`source: "UNAVAILABLE"`), rien dans l'architecture actuelle n'affiche un message explicite au client — le module renvoie simplement une liste vide. Si une UI future (P2B.2) traite silencieusement "liste vide" et "aucune suggestion trouvée" de la même façon sans jamais utiliser le champ `source`, le client pourrait croire qu'aucune adresse ne correspond alors que le service est simplement indisponible. **Atténuation recommandée** : utiliser explicitement `source` côté UI dès P2B.1/P2B.2 (voir `BAN-INTEGRATION-PLAN.md` §4).
- **Risque de confusion entre suggestion et adresse validée** : si une future implémentation UI (non faite ici) transmettait par erreur une suggestion directement à `stepLydie()` sans passer par un message texte normal, cela contournerait implicitement le principe « une suggestion reste une proposition, jamais une validation automatique ». Aucun code actuel ne fait cela, mais c'est un piège identifié à surveiller explicitement lors de la revue de code de P2B.2.
- **Risque de dérive de `normalize()`** : la fonction est dupliquée (et non partagée) dans 3 fichiers (`engine.ts`, `orchestrator.ts`, `extraction.ts`). Le correctif d'apostrophe a été appliqué identiquement aux 3 cette passe, mais rien n'empêche structurellement qu'une future modification n'en oublie une copie. **Amélioration future recommandée** (§3) : envisager un utilitaire partagé.
- **Risque lié à l'absence totale de tests d'intégration réels** : la totalité des 156 vérifications de cette mission sont des tests unitaires (fonctions pures) exécutés via un shim `vitest` maison — aucun test n'exerce le chemin complet HTTP → `route.ts` → Prisma → réponse, puisque cet environnement ne permet pas de faire tourner Next.js. Un bug d'intégration (mauvais mapping de champ entre le JSON reçu et le contexte Lydie, par exemple) resterait invisible jusqu'à un test réel en environnement complet.

## 3. Améliorations futures (non urgentes, proposées pour référence)

- Factoriser `normalize()` dans un unique module partagé (ex. `src/lib/lydie/normalize.ts`) importé par `engine.ts`, `orchestrator.ts` et `extraction.ts`, pour éliminer le risque de dérive entre les 3 copies. Non fait dans cette mission pour rester dans le périmètre strict demandé (corriger le bug, pas refactoriser l'architecture).
- Ajouter un debounce côté UI avant tout appel à `fetchAddressSuggestions()` (voir `BAN-INTEGRATION-PLAN.md` §8, sécurité/débit) — décision d'implémentation P2B.2.
- Étendre `parseFeatures()` (`addressSuggestions.ts`) pour reconnaître un type de résultat BAN "locality" (lieu-dit) séparément, le jour où la décision métier correspondante sera prise (voir `BAN-INTEGRATION-PLAN.md` §6) — actuellement volontairement absent, pas un oubli.
- Envisager un test d'intégration réel (HTTP complet) dès qu'un environnement avec `npm install` fonctionnel sera disponible, pour combler le risque décrit en §2 dernier point.
- Un mécanisme explicite pour que le client "annule" un `addressDraft` en cours (ex. commande "recommencer mon adresse") plutôt que de systématiquement concaténer — actuellement, un fragment abandonné est simplement concaténé au nouveau message et rejeté si incohérent (sûr, mais pas optimal en UX) ; voir `LYDIE-MEMORY-SPEC.md` §7.

## 4. Pièges rencontrés pendant cette session (pour ne pas les reproduire)

- **Confusion entre deux codebases** : des captures d'écran d'une démo séparée (simulée par un autre agent) montraient des textes/flux qui n'existent nulle part dans le vrai dépôt. Résolu en grep'ant systématiquement les chaînes exactes avant tout diagnostic — confirmé zéro correspondance avant de conclure. **Piège à éviter** : ne jamais diagnostiquer un bug rapporté sans d'abord confirmer, par recherche exacte dans le vrai code, que le comportement décrit existe réellement dans ce projet.
- **Arborescence de compilation scratch dédoublée** (`out/src/lib/...` vs `out/lib/...`) causée par deux exécutions de `tsc` avec des `rootDir` différents dans l'espace de vérification temporaire — a produit un faux résultat "toujours en échec" en lisant un fichier `.js` compilé obsolète depuis le mauvais chemin. **Piège à éviter** : après toute modification du `tsconfig.json` de vérification (notamment `rootDir`), toujours `rm -rf out` avant de recompiler, plutôt que de laisser cohabiter deux arborescences.
- **Shim `vitest` maison incomplet** : `toMatch`, `toBeDefined`, `toBeUndefined`, `toBeInstanceOf`, `toMatchObject` étaient absents au départ, causant des échecs de tests préexistants (`lydie-mandat-materialization.test.ts`, `lydie-resume.test.ts`) qui n'avaient aucun rapport avec les modifications de cette session. **Piège à éviter** : face à un échec de test inattendu sur un fichier non touché, vérifier d'abord si le shim de test lui-même supporte le matcher utilisé, avant de suspecter une régression réelle dans le code métier.
- **BAN réellement inaccessible, jamais supposée accessible** : la tentation aurait été de simuler une réponse BAN et de la présenter comme une preuve d'appel réel. Résolu en distinguant explicitement, dans chaque test et chaque rapport, "transport simulé pour isoler la logique de parsing" vs "fetch réel observant un vrai blocage réseau" — jamais présenté l'un comme l'autre. **Piège à éviter** : ne jamais laisser un test avec transport simulé être lu comme une preuve d'appel réseau réussi.
